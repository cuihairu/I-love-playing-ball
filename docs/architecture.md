# 技术选型与目录设计

## 平台目标

- 微信小游戏
- 抖音小游戏

这两个平台都更适合走“一套游戏主工程 + 平台适配层”的方案，而不是分别维护两套前端项目。

## 建议技术路线

### 1. 游戏客户端

建议使用 `Cocos Creator`。

原因：

- 对微信小游戏支持成熟，文档和社区资料相对完整。
- 支持发布到多个小游戏平台，更适合你现在的目标。
- 你有 Unity 和 C# 经验，上手节点、组件、场景这些概念不会太陌生。
- 比直接手写小游戏前端更省时间，尤其适合你目前前端经验偏弱的情况。

### 2. 后端服务

后端拆成两层:薄网关 + 实时玩法服务。2026-08-31 已确定:争霸玩法走实时连接,传输用 WebSocket。

#### 薄网关层(`apps/backend`)

当前实现语言使用 `Go`,Web 框架使用 `Gin`,默认数据库使用 `SQLite`,ORM 使用 `Gorm`。

只承担两类活:

- HTTPS 接口(小游戏平台硬性要求,域名要进白名单):
  - 登录换 session(微信/抖音 code2session)
  - 配置下发
  - 排行榜、勋章、修炼进度提交与查询
  - 广告位和开关配置
  - 素材版本配置
- WebSocket 实时入口:
  - TLS 终结(小游戏端只允许 `wss://`)
  - 登录态鉴权、心跳、转发
  - 断线事件上报

网关原则:不带业务逻辑,只做协议转换和转发。这样网关实现将来可以换,业务不受影响。

不做:

- 不做支付
- 不做复杂商城
- 网关里不写玩法逻辑

#### 实时玩法服务层(自研 shield)

实时玩法运行时使用自研框架 shield:https://github.com/cuihairu/shield ,actor 模型游戏服务器运行时,C++23 运行时 + Lua 写玩法逻辑。

定位:

- 争霸玩法的匹配、房间、实时对战裁决
- 对战结算、段位与勋章计算
- 会话与断线重连恢复(shield 规划中的 `shield_player` 扩展正对这个需求)

接入节奏:

- V1:shield 不在上线关键路径上,但实时消息契约先定好
- V2:shield 承载争霸玩法的房间与对战,通过网关的 WebSocket 链路接入
- shield 侧产出真实业务需求,反哺框架演进

#### 实时链路

```text
小游戏端 wx/tt.connectSocket (wss://)
    |
薄网关(TLS 终结 / 鉴权 / 心跳 / 转发)
    |
shield actor 服务(匹配 -> 房间 -> 对战 -> 结算)
```

约束:

- 小游戏端实时通道只有 WebSocket,微信 `wx.connectSocket`、抖音 `tt.connectSocket`
- 实时玩法按"输入即出招、服务端裁决"的半实时设计,不做 60 帧帧同步:小游戏弱网和切后台场景多,帧同步体验不可控
- 断线重连是硬需求:小游戏切后台连接即断,必须有会话恢复和战斗状态恢复
- 实时消息契约单一来源,放 `packages/protocol`,TS / Go / Lua 三端引用,消息带版本号

### 3. 平台能力封装

平台 API 差异不要散落在游戏代码里，统一收口到 `packages/platform-sdk`。

典型内容：

- 激励视频广告
- 插屏广告
- 登录
- 分享
- 存档
- 平台能力检测

## 推荐目录

```text
apps/
  backend/          # 薄网关:HTTPS 接口 + WebSocket 实时入口
  game/             # Cocos Creator 游戏主工程

packages/
  game-config/      # 共享数值与玩法配置
  platform-sdk/     # 微信/抖音平台能力封装
  protocol/         # 实时消息契约,TS/Go/Lua 三端引用

tools/
  art/

docs/
```

## 建议开发顺序

1. 先做核心玩法原型。
2. 再接广告位和平台能力。
3. 后端只提供最小必需接口。
4. 美术资源最后统一替换成成品图。
5. 实时链路最后接:核心循环先用单机/异步撑住,WebSocket 对战在玩法验证后再上。

## 第一版玩法建议

先不要做太大，建议只做一个 1 分钟内就能玩明白的循环：

- 小鸡角色持球
- 点击或长按控制投篮
- 连续命中触发表情梗图变化
- 失败后结算分数
- 看广告复活一次

这个方向更适合广告变现，也更适合小游戏传播。
